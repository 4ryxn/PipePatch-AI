# Deployment runbook

Preflight: run backend tests, Ruff, mypy, Alembic against temporary SQLite, then web typecheck, tests, and production build. Create Neon PostgreSQL and use its pooled `postgresql://...` connection string only as a Vercel `DATABASE_URL` secret. The backend normalizes that standard URL to SQLAlchemy's Psycopg 3 dialect; developers must not change the scheme manually. Set `AUTH_ENABLED=true` only with a 32+ character generated `JWT_SECRET_KEY` secret. In Vercel import the repository with `backend` as Root Directory; it detects `api/index.py` and `pyproject.toml`. `vercel.json` uses a Vercel route rule—not an internal rewrite—so FastAPI receives the original `/health`, `/readiness`, and `/api/v1/*` ASGI paths. Configure `PIPEPATCH_ENV=production`, `ANALYSIS_MODE=gemini`, `GEMINI_API_KEY`, `AUTH_ENABLED=true`, `DATABASE_URL`, `JWT_SECRET_KEY`, and `SUPPLIER_SEARCH_ENABLED=false`. Never run migrations in a serverless request: manually run `DATABASE_URL='NEON_POOLED_URL' python -m alembic upgrade head` from `backend` once before first deployment.

Create a separate Vercel static-site project with `web` as its Root Directory. After the backend URL exists and `/readiness` returns `ok`, set only `VITE_API_BASE_URL=https://YOUR-VERCEL-HOST` in the web project's build environment; it is public by design. Do not add secrets to the web project. After Vercel assigns the static frontend URL, add that exact origin to backend `ALLOWED_ORIGINS` (comma-separated if more than one). Do not add wildcard origins. Vercel Hobby has cold starts, usage limits, a configured 60-second function maximum, and no durable background task runtime; it is appropriate only for a bounded demo, not production-scale supplier discovery. Roll back by selecting a previously verified Git tag and redeploying it. If migration fails, stop deployment, inspect logs without copying secrets, restore using Neon controls, and redeploy the prior tag.
