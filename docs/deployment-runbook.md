# Deployment runbook

Preflight: run backend tests, Ruff, mypy, Alembic against temporary SQLite, then mobile lint/typecheck/tests. Create Neon PostgreSQL and use its pooled `postgresql://...` connection string only as a Vercel `DATABASE_URL` secret. The backend normalizes that standard URL to SQLAlchemy's Psycopg 3 dialect; developers must not change the scheme manually. Set `AUTH_ENABLED=true` only with a 32+ character generated `JWT_SECRET_KEY` secret. In Vercel import the repository with `backend` as Root Directory; it detects `api/index.py` and `pyproject.toml`. Configure `PIPEPATCH_ENV=production`, `ANALYSIS_MODE=gemini`, `GEMINI_API_KEY`, `AUTH_ENABLED=true`, `DATABASE_URL`, `JWT_SECRET_KEY`, and `SUPPLIER_SEARCH_ENABLED=false`. Never run migrations in a serverless request: manually run `DATABASE_URL='NEON_POOLED_URL' python -m alembic upgrade head` from `backend` once before first deployment.

After the Vercel backend URL exists and `/readiness` returns `ok`, set `EXPO_PUBLIC_API_BASE_URL=https://YOUR-VERCEL-HOST` locally for the build only. Run `cd mobile && npx eas build --profile preview --platform android`; do not put secrets in Expo variables. Keep `render.yaml` as an optional alternative only. Vercel Hobby has cold starts, usage limits, a configured 60-second function maximum, and no durable background task runtime; it is appropriate only for a bounded demo, not production-scale supplier discovery. Roll back by selecting a previously verified Git tag and redeploying it. If migration fails, stop deployment, inspect logs without copying secrets, restore using Neon controls, and redeploy the prior tag.
